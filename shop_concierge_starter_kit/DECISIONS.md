# DECISIONS (assumptions made where the spec was ambiguous)

- T1: data functions take `(conn, shop_id, ...)`; `answer(shop_id, message, *, conn=None, now=None)` opens its own connection if none is given. DB path from `DATABASE_PATH` (default `data/shop_concierge.db`, git-ignored via `*.db`).
- T1: `answer()` is read-only. Logging unanswered questions and saving leads is done by the caller (chat router), never by the answer engine or the AI.
- T1: `unanswered_questions` has an extra `norm` column (lower-cased question without punctuation) so repeats are counted; unique per (shop_id, norm).
- T1: hours use weekday 0=Monday, "HH:MM" 24h, no overnight ranges (open must be before close); several rows per day allowed for split shifts. Times are shown as 12-hour AM/PM. "today/tomorrow/now" use the server's local clock (assumption: server timezone = shop timezone).
- T1: honesty rule: if the question contains a meaningful word that appears nowhere in the shop's data (e.g. "tattoo", "physics"), the engine answers "I don't know" and offers to take details instead of guessing from partial matches.
- T1: a not-found reply deliberately contains no currency symbols or digits.
- T1: reserved slugs also include ftp, smtp, imap, pop, ns1, ns2, webmail, dashboard, login, register, internal, s, demo (the demo shops use `demo-*` names, which are allowed).
- Env: use .venv (python3 -m venv .venv; .venv/bin/pip install -r requirements-dev.txt); run tests with .venv/bin/python -m pytest.
- T3: CSRF uses a random `csrf` cookie plus a form field = HMAC(SECRET_KEY, cookie); works before and after login. Session ids are stored hashed (sha256) in `sessions`. Verification tokens are stored hashed, single use, 48h expiry.
- T3: registering with an email that already exists returns the same "check your email" page (no account enumeration) and sends nothing. There is no "resend link" route yet: an owner whose link expired cannot re-register with the same email (it looks like success but sends nothing). Add a resend route if this shows up in real use.
- T3: mailer.send_email is an in-memory outbox stub until T5 (no real email is sent).
- T3: requests whose Host is not BASE_DOMAIN, www.BASE_DOMAIN or a single-label subdomain get 404 (except /healthz). Owner paths (/register /login /logout /verify /dashboard) are 404 on shop subdomains.
- T3: SECRET_KEY must be 32+ chars and not start with "change-me", otherwise the app refuses to start.
- T4: the chat widget is an iframe of `/embed/{slug}` (the only page allowed to be framed; CSP `frame-ancestors *`), opened by `/widget.js?shop=slug`. This keeps third-party sites from running our code and avoids CORS entirely: the chat API is called same-origin from our own page.
- T4: public chat API (`/api/chat`, `/api/lead`) uses no cookies, so no CSRF token; protected by per-IP limits (chat 30/min, lead 5/hour). A lead is saved only when the customer ticks the consent box (server rejects `consent != true`).
- T4: the owner edits hours as one span per day (plus Closed); split shifts are supported by the data layer and the answer engine but not the form.
- T4: "Suggest FAQ" shows a draft with the question prefilled and an empty answer box (no AI). Nothing is saved until the owner clicks "Approve and add".
- T4: QR code points to `BASE_URL/s/{slug}` (works without wildcard DNS). Set `BASE_URL=http://localhost:PORT` for local runs.
- T4: local click-through: `scripts/seed.py --owner-email ... --owner-password ...` creates a verified dev owner for demo-salon; `DEV_LOG_EMAILS=true` prints verification emails to the console.
- T5: with no SMTP_PASSWORD the mailer runs in memory mode (OUTBOX, nothing sent); with it set, mail is sent from a small background thread pool (2 workers), 10 s timeout, one retry for temporary errors only (never for a wrong password). Logs contain only the error type and SMTP code.
- T5: lead alerts go to the verified owner email(s) of that shop, only after the customer ticked consent. The alert contains the name, contact and question the customer typed.
- T5: `/contact` is the platform's own contact form (sends to CONTACT_RECIPIENT) and is apex-only. Tests clear SMTP_* env vars so they can never send real email.
- T5: `scripts/send_test_email.py` was written but NOT run (no real emails are sent by the agent).
- T6: the AI is tried only when the keyword engine says not found. Order of gates: AI_ENABLED (read at startup; false means no client is ever built), API key present, 5-minute in-memory cooldown, per-shop daily cap (30), platform daily cap (AI_DAILY_CAP), per-IP hourly cap (10, counted only when an AI call would really happen), 300-character input, max_tokens 300. The call attempt is counted before the request, so errors also use up the cap.
- T6: `AI_ENABLED=true` with an empty ANTHROPIC_API_KEY silently disables AI (logged as a warning).
- T6: replies are rejected (then one retry, then keyword fallback) unless strict JSON with exactly the four keys; `found=true` must cite source ids the tools returned this request, and every number in the answer must appear in tool output. This can reject a good answer (safe direction: customer gets the keyword answer plus lead capture).
- T6: refusal and max_tokens stop reasons fall back without a cooldown; real API errors (rate limit, billing, timeout, connection, 5xx, anything unexpected) set the 5-minute cooldown. Only the error class name is logged.
- T6: model call uses effort "low", tool_choice auto (never forced), and for claude-haiku-5* thinking disabled so the 300-token limit is not eaten by reasoning. If CLAUDE_MODEL is changed to another model, check that these parameters are accepted.
- T6: propose_lead returns the staged lead to the widget (`proposed_lead` in the chat response); the form is prefilled and the customer must tick the consent box before /api/lead saves it.
- T6: `eval/run_evals.py --ai` needs AI_ENABLED=true and ANTHROPIC_API_KEY. It has NOT been run live (waiting for the owner's "continue"); the tests run it against a mocked client.
